Shrinking “Hello, world!” ELF Binaries

The work in this post was generated using Claude.

How small can a Linux executable that prints Hello, world! actually be? Starting from two prior benchmarks, Brian Raiter’s 62-byte i386 hello and Nathan Otterness’s 120-byte x86-64 hello, we look at how to shave a few more bytes off each. The techniques below produce a 60-byte i386 binary and an 86-byte x86-64 binary, both printing Hello, world!\n.

Background: what the kernel actually checks

An ELF file has two headers that matter for execution. The ELF header (ehdr) is 52 bytes on 32-bit and 64 bytes on 64-bit. It tells the kernel where to find the program header (phdr), which is 32 bytes on 32-bit and 56 bytes on 64-bit.

We iteratively probed the Linux 6.12 kernel to find which ELF fields it actually checks before executing a binary. These are the fields we found to be required:

Field i386 x86-64
Magic 7F 45 4C 46 required required
e_type 2 or 3 2 or 3
e_machine 3 or 6 0x3E
e_phentsize exactly 32 exactly 56
e_phnum ≥ 1 ≥ 1
p_type 1 (PT_LOAD) 1 (PT_LOAD)
p_flags any with PF_R must include PF_X

In our testing, when the following fields were set to arbitrary values, they did not prevent execution: EI_CLASS, EI_DATA, e_ehsize, e_shoff, e_flags, e_version, p_align, and p_paddr.

i386: 60 bytes

The key idea is to overlay the 32-byte program header on top of the ELF header so they share the same bytes, then encode executable instructions inside header fields that the kernel ignores.

Step 1: Overlap the headers. Setting e_phoff = 4 tells the kernel the program header starts at byte 4 of the file. This means the 32-byte program header occupies bytes 4–35, overlapping most of the ELF header. The overlap works because the byte at offset 4 (EI_CLASS=1) is read as p_type=PT_LOAD=1, and e_phoff itself (value 4) is read as p_flags with bit PF_R set. This is the same technique Raiter used in his 45-byte program. On i386 Linux, a binary without a PT_GNU_STACK segment gets READ_IMPLIES_EXEC, so having only the read permission flag is sufficient.

Step 2: Choose a load address that doubles as code. The entry point address is stored as e_entry in the ELF header. Because the headers are overlapped, e_entry also occupies the p_memsz field of the program header. The CPU will execute these bytes as instructions when it jumps to the entry point, so the load address must be chosen so that its little-endian encoding forms valid i386 instructions. With an entry point at file offset 0x14 and load_addr = 0x05430000, the entry address 0x05430014 encodes as 14 00 43 05 in little-endian, which the CPU decodes as:

14 00   adc al, 0      ; no-op (al is already 0)
43      inc ebx        ; ebx becomes 1 (stdout file descriptor)
05 ..   add eax, imm32 ; consumes the next 4 bytes as an immediate

The add eax instruction’s immediate operand is the next 4 bytes in the file, which happen to be e_phoff = 4. After execution, eax = 4 = the Linux SYS_write syscall number, and ebx = 1 = stdout. Two register setups come for free from mandatory header bytes.

Step 3: Pack the remaining code into unchecked fields. The write syscall needs a pointer to the string (ecx) and a length (edx). mov dl, len goes into the p_filesz field, and mov ecx, msg; int 80h; xchg eax, ebx; int 80h fits into the e_shoff through e_ehsize fields. The Hello, world!\n string itself starts at byte 0x2E, immediately after the last required field (e_phnum at offset 0x2C).

The result is 60 bytes for Hello, world!\n.

Source

; hello60.asm - 60-byte i386 ELF
BITS 32
        org   0x05430000

        db    0x7F, "ELF"       ; 00: magic
        dd    1                 ; 04: EI_CLASS=1       / p_type=PT_LOAD
        dd    0                 ; 08: e_ident pad      / p_offset=0
        dd    $$                ; 0C: e_ident pad      / p_vaddr=0x05430000
        dw    2                 ; 10: e_type=ET_EXEC   / p_paddr lo
        dw    3                 ; 12: e_machine=EM_386 / p_paddr hi
_start:                         ; ----- e_entry points here (0x05430014) -----
        mov   dl, msg.len       ; 14: e_version        / p_filesz  (B2 0E)
        mov   al, 0             ; 16:   "              /   "       (B0 00)
        ; bytes 18-1B = e_entry/p_memsz = 14 00 43 05, executed as:
        db    0x14, 0x00        ; 18:   adc al, 0        (e_entry[0:2])
        db    0x43              ; 1A:   inc ebx          (e_entry[2]) → ebx=1
        db    0x05              ; 1B:   add eax, imm32   (e_entry[3])
        dd    4                 ; 1C: e_phoff=4/p_flags=PF_R; imm32 → eax=4
        mov   ecx, msg          ; 20: e_shoff/p_align/e_flags
        int   0x80              ; 25:   write(1, msg, len)
        xchg  eax, ebx          ; 27:   eax=1
        int   0x80              ; 28:   exit(len)
        dw    32                ; 2A: e_phentsize=32
        dw    1                 ; 2C: e_phnum=1
msg:    db    'Hello, world!', 10
.len    equ   $ - msg

Build and run:

nasm -f bin -o hello60 hello60.asm && chmod +x hello60 && ./hello60

x86-64: 86 bytes

ELF64 headers are larger and the layout differs: p_flags sits right after p_type instead of at the end of the program header. On x86-64, the kernel requires the execute permission flag (PF_X). Unlike i386, there is no READ_IMPLIES_EXEC fallback. These constraints mean the i386 overlapping strategy doesn’t transfer directly.

Step 1: Overlap the headers at e_phoff = 0x18. Setting e_phoff = 0x18 (byte 24) places the 56-byte program header starting at the e_entry field. This is the smallest offset that works: the low 4 bytes of e_entry are read as p_type (which must be 1), e_phoff itself becomes p_offset (value 0x18, small enough to be valid), and the unchecked p_paddr field lands on top of the required e_phentsize. Any smaller offset would push e_type/e_machine into the high bytes of p_offset, producing an offset ≥ 4 GB.

Step 2: Enter at byte 1, inside the magic number. Because e_entry’s low bytes must equal p_type = 1, the entry address ends in ...0001, pointing to file byte 1, in the middle of the 4-byte ELF magic. Bytes 1–3 are the ASCII characters "ELF" = 0x45 0x4C 0x46. In x86-64 long mode, byte values 0x40–0x4F are REX prefixes. When multiple REX prefixes appear in sequence, the CPU uses the last one and treats the next byte as the real opcode. So byte 4 is where real code begins.

Step 3: Use instructions that absorb fixed header bytes. At byte 0x0F, a cmp eax, imm32 instruction consumes the next 4 bytes as a dummy operand. Those 4 bytes are e_type and e_machine (02 00 3E 00), which cannot be changed. A short jmp at byte 0x16 skips over the e_entry, e_phoff, and p_vaddr fields (which must hold specific values) and lands in p_paddr, where the syscall instructions live.

Step 4: Store the string in p_align. Bytes 0x48–0x4F correspond to the p_align field, which the kernel does not check. That provides 8 free bytes; the remaining 6 bytes of the 14-character string extend past the end of the program header.

00  7F 45 4C 46 B0 01 89 C7  48 8D 35 39 00 00 00 3D
10  02 00 3E 00 B2 0E EB 18  01 00 00 00 05 00 00 00
20  18 00 00 00 00 00 00 00  18 00 00 00 05 00 00 00
30  0F 05 B0 3C 0F 05 38 00  01 00 00 00 00 00 00 00
40  01 00 00 00 00 00 00 00  48 65 6C 6C 6F 2C 20 77
50  6F 72 6C 64 21 0A

This is 86 bytes total. The ELF header and program header overlap by 40 bytes.

; hello64_86.asm - 86-byte x86-64 ELF
BITS 64
        org   0x500000000

        db    0x7F                   ; 00: magic[0]
_start:                              ; entry @ byte 1: "ELF" = 3 REX prefixes
        db    "ELF"                  ; 01: magic[1:4] = 45 4C 46 = REX.B,.WR,.RX
        mov   al, 1                  ; 04: e_ident pad - first real opcode
        mov   edi, eax               ; 06:   rdi=1 (stdout)
        lea   rsi, [rel msg]         ; 08:   rsi=&msg (rip-relative)
        db    0x3D                   ; 0F: cmp eax, imm32 - eats next 4 bytes:
        dw    2                      ; 10: e_type=ET_EXEC
        dw    0x3E                   ; 12: e_machine=EM_X86_64
        mov   dl, msg.len            ; 14: e_version
        jmp   tail                   ; 16:   → 0x30 (p_paddr)
        dd    1                      ; 18: e_entry[0:4]  / p_type=PT_LOAD
        dd    5                      ; 1C: e_entry[4:8]  / p_flags=PF_R|PF_X
        dq    0x18                   ; 20: e_phoff       / p_offset = 0x18
        dq    $$ + 0x18              ; 28: e_shoff       / p_vaddr
tail:   syscall                      ; 30: e_flags...     / p_paddr - write()
        mov   al, 60                 ; 32:
        syscall                      ; 34:                 - exit()
        dw    56                     ; 36: e_phentsize=56
        dw    1                      ; 38: e_phnum=1     / p_filesz[0:2]
        dw    0, 0, 0                ; 3A: e_sh*         / p_filesz[2:8]
        dq    1                      ; 40:               / p_memsz=1
msg:    db    'Hello, world!', 10    ; 48:               / p_align + tail
.len    equ   $ - msg

Build and run:

nasm -f bin -o hello64_86 hello64_86.asm && chmod +x hello64_86 && ./hello64_86
